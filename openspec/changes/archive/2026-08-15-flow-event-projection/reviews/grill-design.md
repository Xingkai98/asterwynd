# Grill Design: flow-event-projection

## Confirmed Decisions

- **决策**：**决策 1** — design.md 断言「当代事件（change_created 开头、无 handoff.json）replay 直接抛错」准确，且本 change 自身就是首批受影响对象。`replay_handoff_projection` 首事件非 `initialized` 即抛错（`agent/workflow/event_log.py:210-212`），flow-event-projection 自己的 `workflow-events.jsonl` 首事件就是 `change_created`（`openspec/changes/flow-event-projection/workflow-events.jsonl:1`），当前对任意当代 change 调用 replay 都会抛 `workflow-events.jsonl must start with initialized event`。两代分裂修复（D2）必要且必须作为 P1 实现的一部分验证到本 change 自身。（证据：`agent/workflow/event_log.py:210-212`，`openspec/changes/flow-event-projection/workflow-events.jsonl:1`；理由：design.md Context 首条「事件基建两代分裂」是真实代码事实，非假设。）
- **决策**：**决策 2** — D7 声称的受保护路径条目已由 P0 全部落实，任务 3.5 的「补全 governance」实际无需改动策略表。`scripts/flow-policy.json:46-49` 已有 `workflow-events.jsonl`（contains/cli_written），`:70-74` 已有 `workflow-state.json`（contains/cli_written）；guard 内嵌默认表 `scripts/workflow_guard.py:79/:84` 已同步两条。`policy-validate` 有磁盘表==默认表 parity 测试（`tests/test_flow_policy.py` parity 段），因此 P1 若改策略表必须同步改 guard 内嵌默认表，否则 parity 测试失败。（证据：`scripts/flow-policy.json:46-49,70-74`，`scripts/workflow_guard.py:79,84`；理由：D7 是「已存在事实的确认」，不是新增写路径。）
- **决策**：**决策 3** — `_is_privileged_cli` 豁免正则只含 `artifact-event|review-manifest|policy-[a-z-]+`，不含 `flow`（`scripts/workflow_guard.py:266-272`）。`flow confirm/approve` 写 `workflow-events.jsonl`（cli_written 受保护）与 `workflow-state.json`（cli_written 受保护），当前 `flow` 调用会被 Bash 写意图保护路径检查拦截（`:571-578` exit 2）。实现必须扩展豁免正则；且 `flow` 子命令若仿 `policy-[a-z-]+` 用通配，需同时确认 `:264` 复合命令检查（`&&`/`;`/`|`/反引号/`$()`/换行/重定向）足以挡住 `flow status --change X && echo x > workflow-state.json` 类 hijack。（证据：`scripts/workflow_guard.py:254-272,571-578`；理由：新命令组写受保护路径必须走合法 CLI 通道，否则 guard 自拦。）
- **决策**：**决策 4** — 当代事件日志含大量 replay 无法处理的事件类型，design D2 字面「当代事件走 `_apply_*_event` 链」不成立——链上无这些类型的处理器。实测事件日志中的 `change_created`、`grill_completed`、`design_review_completed`、`building_review_completed`、`known_debt_updated`、`design_reviewed` 均不在 `NON_STATE_EVENT_TYPES`（`agent/workflow/event_log.py:17-23`），也无一对应 `_apply_*_event` 分支，replay 会落入 `else: raise StateMachineError("unknown workflow event type")`（`:231-232`）。这些类型真实存在于 archive 的 `2026-08-09-web-multi-session-entry`（grill_completed/design_review_completed/building_review_completed）、`2026-08-14-flow-policy-source`、`2026-08-09-fix-issue-110` 等当代事件日志。统一投影必须为每个现存事件类型补充「NON_STATE 跳过 或 milestones 派生」的明确映射，否则「任意 change 可投影」目标在 archive 当代 change 上落空。（证据：`agent/workflow/event_log.py:17-23,221-232`，事件日志 `openspec/changes/archive/2026-08-09-web-multi-session-entry/workflow-events.jsonl`；理由：两代分裂修复的范围是「全部现存事件日志」，不限于本 change。）
- **决策**：**决策 5** — 旧 `cmd_approve` 语义与 `flow approve` 产物不同，且存在 live 引用，删除/改造影响面已确认。`cmd_approve`（`scripts/workflow_state.py:554-618`）写 `.handoff/<id>/gate-approvals.json`（guard_only 受保护）并调 `WorkflowManager.human_approve`（`:591`）；live 引用方：`cmd_discover_json` 输出的 `approve_command` 字符串（`:411`，discover 是主命令）、模块 docstring（`:11-12`）、`tests/test_workflow_state_cli.py` 4 个 advance/approve 测试（`:20-110,:307-313`）。删除 advance/approve 必须同步改 discover JSON 输出（否则输出指向不存在的命令）与删/改测试；历史引用在 `openspec/changes/archive/2026-07-14-add-workflow-automation/`（归档，不构成 live 调用方）。（证据：`scripts/workflow_state.py:411,517-618`，`tests/test_workflow_state_cli.py:20-110,307-313`；理由：Q2 决策前必须知道完整调用面。）
- **决策**：**决策 6** — D6「verify 扩展覆盖新世代」在现有代码没有可复用接入点，必须新建。`verify_handoff_projection` 对无 handoff.json 的 change 直接返回 `handoff.json missing`（`agent/workflow/event_log.py:320-322`）；checker 侧 `_check_handoff_json` 在 handoff.json 不存在时直接返回 []（`scripts/check_openspec_artifacts.py:891-894`），当代 change 完全不经过 replay 验证。D6 的「磁盘投影==replay」一致性检查需要一个新的 checker 入口（如 `_check_workflow_state_projection`），不能靠改 `_check_handoff_json` 复用。（证据：`agent/workflow/event_log.py:319-331`，`scripts/check_openspec_artifacts.py:891-894,956-959`；理由：当代 change 无 handoff.json，现有 verify 的「handoff.json == replay」比较基准不成立。）
- **决策**：**决策 7** — `_all_change_ids` 只列有 handoff.json 的目录（`scripts/workflow_state.py:173-180`），`discover` 已漏掉所有当代 change。`flow status --all` 若复用该函数则同样看不到当代 change（flow-event-projection / add-worktree-tool 等），必须改为「handoff.json 或 workflow-state.json 或 workflow-events.jsonl 任一存在」的遍历条件。（证据：`scripts/workflow_state.py:173-180`；理由：`flow status --all` 的设计目标是混合世代目录可读，现有遍历函数不满足。）

## Open Questions

- **Q1**: `flow status` 的输出形态——纯文本表格（手机可读）还是 JSON + 文本双格式？现有 `discover` 已是双格式（`scripts/workflow_state.py:914-915` 的 `--format text|json`），`flow status` 是否对齐？若对齐，`--format` 的 choices、`--change`/`--all` 互斥关系、每行字段（state/milestones/last_seq/stale）需在 parser 定义时定死。为什么必须现在定：这是 `flow` parser 与 `tests/test_workflow_state_cli.py` 集成测试的接口契约。
- **Q2**: 废旧 `advance`/`approve` 的处理——直接删除还是保留兼容提示？live 调用面已确认（决策 5）：`discover --format json` 输出的 `approve_command` 字符串（`workflow_state.py:411`）、模块 docstring（`:11-12`）、`tests/test_workflow_state_cli.py` 4 个测试。删除需要同步改 discover 输出与删/改测试；保留兼容提示需要定义提示文本（如「已废弃，请用 flow approve」）与是否保留 `--to-phase`。为什么必须现在定：影响任务 3.2 与测试 2.7，且 discover 输出引用废弃命令会产生「文档/命令指引到不存在命令」的破面。
- **Q3**: guard stale 兜底的精确语义——「现有正则兜底」并不存在于当前 guard。`workflow_guard.py:533-600` 的 main() 只有受保护路径检查 + grill gate，没有任何 awaiting 判定逻辑；所谓「正则兜底」需要 P1 从零定义。设计 D5 的「投影缺失/损坏/stale → 回退正则兜底」要落到什么正则？（例如：读 workflow-events.jsonl 末条 `blocked_entered`/`blocked_resolved` 判断 awaiting 与是否已确认？正则如何识别「确认」？）「awaiting 且已确认」如何与投影判定对齐（决策 4 已知 blocked_resolved 是 blocked 事件的解开，正则兜底能否覆盖）？为什么必须现在定：guard 是执法权威，兜底语义不清会导致 awaiting 执法误放行/误拦截。
- **Q4**: `awaiting_proposal_confirmation` 留槽位暂不派生的边界——当前没有任何当代写路径写 `blocked_entered`（唯一写点是 `WorkflowManager.block`，`agent/workflow/manager.py:307-322`，依赖 handoff.json 老世代）。若 P1 完全不产出该态，`flow confirm` 无可确认对象（见 Q9）；若保留派生逻辑但守卫禁用，派生规则和 seed 从哪来？为什么必须现在定：D1 把三个 awaiting 态列为投影字段，但「留槽位暂不派生」与「flow confirm/approve 有东西可确认」是同一硬币两面，Q4 与 Q9 必须一起拍板。
- **Q5**: checker 派生物一致性对归档 change 是否生效（`--check-archived` 是否扩展）？`_check_review_manifests` archived=True 分支只做 review manifest drift 检测，不做投影一致性（`scripts/check_openspec_artifacts.py:1025-1026,1046-1048`）。若扩展，archive 下当代 change（web-multi-session-entry 等）也要「磁盘投影==replay」校验，但这些 change 归档时没有 workflow-state.json——是允许缺失还是要求回填？为什么必须现在定：决定新检查是仅 active change 还是全量，影响任务 2.6 测试范围。
- **Q6**: 投影生成时机——每次 CLI 调用即时 replay（无落盘，纯派生）还是落盘 `workflow-state.json` 缓存 + stale 校验？design D1/tasks 3.2 写「落盘 + source_event_seq」，但落盘目标是 cli_written 受保护路径（Write/Edit 被 guard 拦 `workflow_guard.py:558-565`），写入者只能走 `flow` CLI 自身。若即时 replay 无落盘，则磁盘上无 workflow-state.json，D5「guard 读投影」与 D6「磁盘投影==replay」都失去比较对象——两个子设计相互依赖，必须整体定方案（含「flow status 是否触发落盘」这个写路径触发时机）。为什么必须现在定：这是实现架构的第一岔路口，影响 guard/checker/flow 三处。
- **Q7**（新增，代码层）: 统一投影入口的输出形状——`replay_handoff_projection` 返回 handoff 形状（state/transitions/blockers/last_gate/next_hints，`event_log.py:214-234`），而 workflow-state.json 是 `state + milestones + source_event_seq` 新形状。D6「磁盘投影 == replay 投影」的比较对象是哪个形状？`milestones` 从哪些事件派生（archive 当代日志中的 `grill_completed`/`design_review_completed`/`building_review_completed` 是否就是 milestones 来源，见决策 4）？`source_event_seq` 从当代事件链怎么算（`_append_event` 用 `seq = len(events)+1`，`event_log.py:198`，即 len(events)==max seq，是否直接取 len(events)）？为什么必须现在定：决定新增一个「workflow-state 形状的投影函数」还是「改造 replay 输出形状」，两者都不向后兼容现有 handoff.json 消费者。
- **Q8**（新增，代码层）: 当代事件首事件 `change_created` 不在 `NON_STATE_EVENT_TYPES`（`event_log.py:17-23`），且无 `initialized`/handoff 提供初始 state 种子。`change_created` 应加入 NON_STATE 跳过，还是作为派生起点？若为派生起点，初始 phase/sub_state 从哪来（flow-event-projection 自身仅 change_created+backlog_updated 两事件，能投影出什么 state？）？为什么必须现在定：flow-event-projection 自己的 `flow status` 就是第一个测试用例，seed 定义直接决定输出。
- **Q9**（新增，代码层）: `flow confirm` 写 `blocked_resolved` 的 payload 来源——`append_unblocked_event` 需要 `transition`（from.phase==blocked）+ `blocker_index` + `blocker`（`event_log.py:89-107`），`_apply_unblocked_event` 校验 `transition["from"]["phase"] == "blocked"` 且 `blocker_index` 必须落在现有 `blockers` 数组内（`:287-295`）。P1 无 `blocked_entered` 写路径（见 Q4）时，`flow confirm` 写什么 transition（从 blocked 恢复到哪个 phase/sub_state）？blocker 内容（blocked_from/reason/blocked_at/resolved_at，spec `openspec/specs/dev-workflow-state-machine/spec.md:295-300`）从哪来？为什么必须现在定：confirm 的命令契约（参数与事件 payload）是用户可感知的界面，且直接决定 Q4 能否成立。
- **Q10**（新增，代码层）: guard 豁免正则扩展 `flow` 的防 hijack 边界——`:264` 复合检查（`&&`/`;`/`|`/反引号/`$()`/换行/`>` 重定向）已拦链式命令，但 `flow` 子命令是否应像 `policy-[a-z-]+` 那样在正则内白名单化（`flow\s+(status|confirm|approve)`），避免 `flow --help`/`flow <任意>` 等任意参数被豁免？若白名单化，未来新增 `flow 子命令`（如 P2）每次要改 guard 正则 + parity 测试。为什么必须现在定：`_is_privileged_cli` 的 `flow` 分支是本 change 的安全关键改动，hijack 面要与 `test_flow_policy.py:399-405` 的链式 hijack 测试对齐。
- **Q11**（新增，代码层）: D6「verify 扩展覆盖新世代」的精确语义——`verify_handoff_projection` 无 handoff.json 直接返回错误（`event_log.py:320-322`），当代 change 无 handoff.json。扩展是改 verify 以 workflow-state.json 为比较基准，还是 checker 新增独立「从事件 replay 重建投影」函数做对比（见 Q7 形状问题）？归档当代 change（web-multi-session-entry 等）无 workflow-state.json 时该检查是跳过还是报错？为什么必须现在定：与 Q5/Q7 耦合，三处一起构成 D6 的完整定义。
- **Q12**（新增，代码层）: D4 说 `blocked_entered` 只由「进入 awaiting 的完成命令」写——现有唯一写点是 `WorkflowManager.block`（`agent/workflow/manager.py:307-322`，依赖 handoff.json 老世代）。P1 是否给 proposal/design 完成命令新增 `append_blocked_event` 调用点（如 `/opsx:propose` 完成后写 awaiting_proposal_confirmation），还是完全留给 P2？若留 P2，则 P1 的 `flow confirm`/`flow approve` 只能作用于 P2 产出的 awaiting 态，P1 自身的 awaiting 执法没有测试对象。为什么必须现在定：决定 P1 交付时 `flow confirm` 是否可用（有无真实 awaiting 可确认），与 Q4/Q9 同源。

## Risks

- **两代兼容回归（高）**：replay 修复（D2）与统一投影（Q7/Q8 的映射）可能改变老世代投影结果（handoff 形状的 state/last_gate/next_hints 派生），且当代事件类型映射不全会让 archive 现代 change 仍抛错——缓解：parity 测试锁「老世代 replay 结果与修复前一致（golden 断言）+ 当代事件 replay 不抛错」；枚举全量现存事件类型（决策 4 已列）并逐个单测。
- **guard 豁免扩展被 hijack（中）**：`flow` 加入 `_is_privileged_cli` 后，若子命令不白名单化，`flow <任意参数>` 或复合命令可能绕过受保护路径检查——缓解：子命令白名单正则 + 复用 `:264` 复合检查 + 扩展 `test_flow_policy.py:399-405` 的 hijack 用例矩阵；fail-closed（不匹配不豁免）。
- **advance/approve 删除破坏 discover 输出（中）**：`cmd_discover_json` 的 `approve_command`（`workflow_state.py:411`）在 `discover --format json` 时输出到每个 gate 态 change，删除 approve 后该命令指向不存在子命令——缓解：同步更新 discover 输出为 `flow approve` 或删除该字段，并更新对应测试。
