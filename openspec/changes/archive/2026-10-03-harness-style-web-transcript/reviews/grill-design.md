## Open Questions

- **Q1**: 折叠行的失败判定要不要对齐后端自己的错误前缀集（即把 `[Error` / `Error` / `[Permission denied` / `[Approval denied` / `[Approval unavailable` / `[MCP tool error` / `Task ... status: failed` / 非零 `exit_code:` 行并入 `FAILURE_PATTERNS`），并把未锚定的 `failed\s+with\s+exit…` 收紧？；推荐: 必须并入（这是 L4 的主路径），同时把 `failed\s+with\s+exit` 锚定或要求前缀为 `command `，并补 node 测试 + 用**真实 Bash JSON** 重写浏览器 L4；依据: `transcript.js:118-129`、`loop.py:103-111`、`loop.py:936-947`、`registry.py:142-156`、`transcript.js:127`（唯一未锚定模式，注释却写「锚定行首」）；例子: 场景一（漏报）：用户让 agent 删除一个文件，`Bash{cmd:"rm -rf build"}` 在 read_only 模式下触发审批且被拒 → 服务端发 `result = "[Approval denied: tool Bash was not approved in read_only mode: <reason>]"`（`loop.py:936-940`）→ 现在 UI 折叠行是 `▸ Bash · rm -rf build · 118 字符`（灰、无错误色，用户以为成功了），点开才看到被拒；修好后同一行应为红色 `▸ Bash · [Approval denied: tool Bash was not approved in read_only mode: …`。场景二（误报，且在本仓库内可复现）：`Grep{pattern:"command failed with", path:"tests/"}` 成功返回，首行 `tests/web_tests/test_transcript_js.py:221: for text in ("exit code 1", "Exit code: 2\nstdout…", "command failed with exit status 128"):`（`grep.py:61` 的 `f"{f}:{i}: {line}"`）→ 未锚定模式命中行中的 `failed with exit status 128`，捕获组 `128 ≠ 0` → 折叠行被标红成 error，而这次 Grep 完全成功（node 实测：`summarizeToolResult('Grep','agent/x.py:3: msg = failed with exit code 3') → {"state":"error"}`）。

- **Q2**: Bash 失败时，折叠摘要该显示「原始命令」还是「结果首行」？（Bash 的 `tool_result.result` **永远是单行 JSON**，`to_json()` = 整段 stdout/stderr 转义后的一行，所以 D4 的「首行」= 整个 JSON 信封）；推荐: 结构化工具（Bash/TaskOutput）失败时**保留参数摘要**（命令是第一定位符），把失败信号放行尾 meta（`exit 1 · 2.1k 字符`）+ 错误色，必要时把首行截断到 body 顶部；只有非结构化文本工具用「首行替换摘要」；依据: `bash.py:159-165`（成功也返回 `result.to_json()`，超时/OOM 返回 `ToolResult(text=result.to_json())`）、`sandbox/base.py:117-118`、`transcript.js:467-470`（失败时无条件 `setText(row.__summaryEl, verdict.summary)` 覆盖参数摘要）、`test_transcript_js.py:226-230` 与 `test_transcript_view_browser.py:267` 用的是 `[Exit 1] …` / `[Timeout after 30000ms] …`——那是 `SandboxResult.__str__`（`sandbox/base.py:109-115`）的格式，而 `__str__` 在全仓没有任何生产消费点（全仓 grep：只有 `bash.py` 调用 `sandbox.run`，且一律走 `to_json()`）；例子: `Bash{cmd:"uv run pytest -q"}` 跑出 1 failed / 12 passed → 事件里的 result 是 `{"exit_code": 1, "stdout": "1 failed, 12 passed\n…", "stderr": "", "duration_ms": 7345.2, "timed_out": false, "oom_killed": false, "degraded": false}`（`bash.py:165` + `base.py:117`）；现在折叠行渲染成 `▸ Bash · {"exit_code": 1, "stdout": "1 failed, 12 passed…`（红色、120 字符截断），**命令 `uv run pytest -q` 消失**；按推荐改法应为 `▸ Bash · uv run pytest -q · exit 1 · 2.1k 字符`（红）。注：`test_transcript_view_browser.py` 的 L4 用 `"[Exit 1] no tests ran"` 这个**Bash 永不产出**的形态，所以测试绿而生产样貌不同——这是测试保真问题，不只是观感问题。

- **Q3**: 参数（args）要不要也套 `BODY_LIMIT`，以及抽屉的「（参数已截断）」提示要不要移到**可见**位置？；推荐: 两件都做——`createToolRow` 里对 `prettyArgs()` 结果调 `formatBodyText(…, BODY_LIMIT)`；`arguments_truncated` 的提示写到 head 行（例如 meta 位或 summary 前缀），或让 body 在参数被截断时默认可见；依据: `transcript.js:390-395`（args 走 `prettyArgs` → `JSON.stringify(parsed, null, 2)`，**无任何长度上限**，`:421-430`）、`transcript.js:459`（只有 result 走 `formatBodyText`）、`transcript.js:397-400`（note 建在 body 内且 `hidden = true`）+ `:386-388`（body 本身 `hidden`）、`workflow_transcript.js:436-442`（只把 note.hidden 置 false，父节点仍 hidden）、`loop.py:1024-1028`（非审批路径发的是**原参数**，不是 redacted；`agent/approval.py:160-183` 的 `redact_value` 不截断，只有 `summarize_arguments` 的 2000 字符上限是给审批卡用的）；例子: 场景一：模型调 `Write{path:"gen.py", content:"x"*5_000_000}` → `tool_call` 事件带 ~5MB 参数 → `JSON.stringify(args,null,2)` ~5MB 写进 hidden body → 浏览器里是一个 ~10MB（UTF-16）文本节点，而折叠态**一个字符都看不到**，`formatBodyText` 的 200000 上限对它不生效（对照 result 侧有上限）；场景二：抽屉打开某节点「对话」tab，该节点的工具调用参数被 transcript 投影无条件截断（`arguments_truncated: true`，`agent/subagent/manager.py:90-118` 的 `TRANSCRIPT_ITEM_LIMIT = 4000`，经 `agent/subagent/manager.py:132-156` 投影、`web/session.py:945-956` 透传）→ 代码把 `（参数已截断）` 写进 `.tool-row-note` → 但 note 是 `hidden` body 的子节点，用户在抽屉里**永远看不到这个提示**，只能点开行才看到；`test_workflow_graph_browser.py:951` 的 `assert "参数已截断" in body`（`text_content`）依旧绿 → 测试无法发现「提示不可见」。

- **Q4**: `pendingToolRows` 的兜底策略：要不要在 `done`/`error` 清空，并把「同名优先取最早」改成「取最近（队尾）」？；推荐: 两者都做（各 1-2 行），并补一条合成事件的配对顺序回归；依据: `chat.js:800-808`（`findIndex` 找**最早**同名项 + `if (index === -1) index = 0` 取队首）、`chat.js:617-620`/`:644-654`（`tool_call`/`done`/`error` 分支都不清理 pending）、`chat.js:1029`（`takePendingToolRow(name) || newToolRowFromResult(payload)`）；`loop.py:1024-1037` 两个 `await` 之间没有挂起点，所以「有 call 无 result」只在**结果载荷构造抛异常**（`extract_text` / `summarize_tool_result` 在同一 dict 字面量里、位于 `on_event("tool_call")` 之后）这种窗口才可能出现——我未能构造出可达的真实触发路径（**未验证**：需要一次真实 run 或 fault injection 才能证实）；例子: 假设第 1 轮 `Read` 的 `tool_result` 因载荷构造异常没发出 → 第 1 轮的行永久停在 `▸ Read · agent/loop.py · 运行中`（`data-state="running"`，meta 琥珀色，`style.css:488-491`）；第 2 轮模型又调 `Read{path:"web/session.py"}` → 新行入队，队里此时是 `[第1轮Read, 第2轮Read]`；结果到达时 `findIndex` 命中**最早**那条 → 第 1 轮的行被写成 `web/session.py` 的结果、第 2 轮的行永远「运行中」——两张行都错，且没有任何 UI 信号。改成取队尾（或 `findLastIndex`）后，第 2 轮的行正确收尾，第 1 轮的僵尸行在 `done` 清空后被回收。

- **Q5**: L2 的 4000 字符预算是否过松、要不要改成结构性断言？；推荐: 收紧到「折叠态可见文本 ≤ 1200 字符」或直接断言每个 `.tool-row-summary` 与对应结果的前 200 字符无交集（结构断言比总量断言更能定位），并把 proposal 的对照口径从「≥100000 字符」改为实测的 ~24000；依据: `test_transcript_view_browser.py:32-37`（`VISIBLE_TEXT_BUDGET = 4000`，注释自称「旧实现 ~24000 字符起步」）、`test_transcript_view_browser.py:180-186`（两条断言：总量 + `"x"*200 not in visible`）、旧实现的可见文本确实 = 20 × `display.preview` 1200 = 24000（`agent/tool_result_display.py:50-55` + git diff 中删除的 `body.textContent = display.collapsed ? display.preview : fullResult`），而 proposal.md 的 L2 行写的是「对照现状：**≥ 100000 字符**」——口径写错了 4 倍；例子: 实现 20 行后实测每行可见文本 ≈ `▸`(伪元素不计) + `Read`(4) + ` ` + `src/file_0.py`(13) + ` ` + `5.0k 字符`(7) ≈ 26 字符 → 总计 ≈ 600 字符，预算 4000 有 6.6 倍余量。做变异：把折叠行摘要从「参数摘要」改成「结果前 150 字符」→ 20 × 150 + 600 = 3600 < 4000 ✓，且 `"x"*200` 仍不在可见文本里（每行只泄漏 150 < 200）✓ → **两条断言全绿，而刷屏已经回来了**。这正是本项目最怕的「假保护」形态。

- **Q6**: 历史回放要不要带回工具名（D6 说需要「给 `Message` 加字段并穿透三个 provider」，实测成本被高估）？；推荐: 至少在 spec 里把「历史工具行永远无工具名」写成**已知限制**；若愿意动 web 层，给 `build_history_payload` 的每条消息加 `tool_call_id`（`Message` 已有，`agent/message.py:151`）与 assistant 的 `tool_calls`（`:152`，`Message.to_dict` 已序列化，`:172-176`），前端用 `tool_call_id` 反查前一条 assistant 的 `tool_calls[].name` 即可把标题从「工具结果」变成真名——这是 `web/session.py:61-70` 一处改动 + 前端映射，不是协议/三 provider 改造；依据: `web/session.py:43-72`、`agent/message.py:146-177`、`tests/web_tests/test_session.py:975-1005`（两条历史断言只检查 `reasoning` 字段与「opaque 不外发」，**不**钉 key 集合，加字段不会破）；例子: 一次真实 run 里有 12 次工具调用，重连后 `build_history_payload` 发 12 条 `role:"tool"`；现在 UI 是 12 行一模一样的 `▸ 工具结果 · <结果首行> · 135 字符`，用户无法分辨哪条是 `Bash`、哪条是 `Read`、哪条是失败的；若带上 id/name，同样的 12 行变成 `▸ Bash · uv run pytest -q`、`▸ Read · web/static/chat.js`（标题 + 参数摘要都回来），这也是 D6 的 Non-Goal「不让历史回放拿回工具名」真正的代价所在。

## 风险

- **R-A（高，MUST-FIX）**: 失败判定与后端 canonical 错误通道不对齐（`transcript.js:118-129` vs `loop.py:103-111` + `registry.py:142-156` + `loop.py:936-947`），导致参数解析失败、未知工具、工具抛错、权限/审批拒绝、MCP 错误这些**最常见的失败**在折叠行上显示为成功（灰色、无错误首行）。L4 验收在真实链路上不成立（现有 L4 只用 `[Exit 1]` 这个 Bash 不产出的形态）。
- **R-B（中）**: Bash 失败摘要覆盖掉命令（`transcript.js:467-470` + `bash.py:165` 的单行 JSON），用户看到的定位符变成 `{"exit_code": 1, "stdout": …`；行尾 meta 的 `char_count` 也变成 JSON 信封长度（`echo hi` 的命令显示「135 字符」而不是 2），对「结果有多大」的判断失真。
- **R-C（中）**: 展开正文的 200000 上限只作用于 result，**args 无上限**（`transcript.js:390-395`），`Write`/`Edit` 大参数会塞进 hidden body；`.tool-row-note`（`transcript.js:397-400`）藏在 hidden body 内，抽屉的「（参数已截断）」提示实际不可见，且 `text_content` 型断言无法发现。
- **R-D（中）**: 大结果的成本远高于 R7 的「低」评级：服务端对 `tool_result.result` 无任何上限（`loop.py:1031` 直接发全文；`display.preview` 只截预览，`tool_result_display.py:55`），已知上限只有后台任务 stdout 64KB（`agent/background.py:13`）、subagent 结果 30000 字符（`agent/subagent/manager.py:67-78`）、工作流节点 transcript 4000 字符（`web/session.py:739`）——**都不在 chat WS 路径上**。前端 `JSON.parse` 全量入内存后只保留 200000 字符进 DOM（`transcript.js:459-463`），且 `textContent += '…'` 会再把 200k 字符串重建一次。最坏情形：`Read` 一个 5MB 文件 → WS 帧 ≈ 1–2× 结果大小（Bash 的 stdout 若全是换行/引号，经 `to_json()` 内层转义 + 外层 JSON 再转义后可达 ~4×，此项为推算、**未实测**）→ 折叠态仍付全量网络 + 解析 + 200k 字符文本节点的代价，「折叠态零成本」不成立。真正的放大器是 `renderHistory`：重连时把**所有**历史工具消息一次性 `appendHistoryToolResult` 成行（`chat.js:751-757` + `:776-792`），每条最多写 200k 字符 → 100 条大结果 ≈ 2000 万字符（~40MB UTF-16）的主线程同步 DOM 构建。
- **R-E（低-中）**: 残留 pending 行 + 「取最早同名」的错配（见 Q4）会同时制造「永久运行中」和「结果贴错行」两种错误，且没有任何 UI 信号；`done`/`error` 不清理 pending 使僵尸行可以跨轮存活。
- **R-F（低）**: pending row 的跨 tab 泄漏经逐路径推演**未发现**可达路径：`bindActiveTab` 同时设置 `activeTabId` 与全部全局代理（`chat.js:211-244`）、`syncActiveTab` 写回 `getActiveTab()`（`:246-264`），二者恒一致；`closeTab` 先把 tab 从 `tabs` 删除（`:343-354`），此后 `getActiveTab()` 返回 undefined，`syncActiveTab` 提前返回，不会把死 tab 的数组写进活跃 tab。**但** `onclose` 里无条件的 `bindActiveTab(tab)`（`chat.js:445-461`，**本 change 未改**）会把全局 chrome（sessionId/mode/status/`messagesEl`）指向一个已关闭 tab 的脱离 DOM，属既有缺陷、被新增的 `pendingToolRows` 代理放大了一个面，建议顺手加 `tabs.has(tab.id)` 守卫。
- **R-G（低）**: 观感/一致性小项——相邻工具行的 2px 导轨被 3px `margin-top` 断开（`style.css:412-418`）与 D9 的「连成一组」不符；抽屉历史行一律 `data-state="running"`（`transcript.js:352`）；`.message.tool` + `addMessage` 的 tool 分支（`chat.js:888-893`、`style.css:209-217`）是死代码；`.tool-row-meta` 对大结果会渲染成 `1048.6k 字符` 而不是 `1.0M 字符`（`transcript.js:309`，node 实测）。
- **R-H（低，未验证）**: 多文件零构建前端的缓存组合风险——若浏览器复用了旧 `index.html`（`web/server.py:144-149` 用 `HTMLResponse(html)` 直出、无 `Cache-Control`/`ETag`，而 `/static` 走 `StaticFiles` 有 ETag/Last-Modified，`:140`），旧 HTML 不会加载 `transcript.js`，但 `chat.js?v=25` 是新文件 → `transcriptApi()` 返回 `undefined` → `createToolRow` 抛 TypeError → `handleEvent` 整条事件被吞（WS `onmessage` 不 try/catch，`chat.js:441-444`），工具行静默消失。是否真会命中取决于浏览器对无验证器 HTML 的启发式缓存策略（**未验证**）。
- **R-I（流程，非设计缺陷）**: 本 worktree 里实现代码（`web/static/transcript.js` 新增 + `chat.js`/`style.css`/`index.html`/`workflow_transcript.js` 修改 + 两个测试文件）**已经写完**，而 `openspec/changes/harness-style-web-transcript/` 下只有 `proposal.md` 与 `design.md`（无 `tasks.md`、无 `specs/` delta、无 backlog 记录），grill 是按 AGENTS.md 应当在写代码前完成的关；本文件的 Open Questions 必须逐条交用户确认并写入 `## User Confirmation` 后才算闭环（我作为零记忆 reviewer 不代答）。

## 结论

**verdict: 方向可实施、骨架可保留，但按当前 design.md 原样落地会让 L4 验收在主路径上假绿——必须订正后再实现。** D1/D2/D3/D6/D7/D8/D10 的结构选择经源码核对成立（`.message` 骨架不动、无 turn 包装层、折叠态零可见正文、body 为头部兄弟节点、类名兼容保留都是对的，参考实现行号引用也逐条对得上）；D5 的「不需要协议 id」结论正确但风险叙述说错了地方；D9/D11/D12 的表述与实现/测试不符，需回写设计。实现层已有的代码与本设计的偏差集中在**失败判定**与**尺寸上限**两处，属于「看起来完成度很高、但最关键的一条验收是假绿」。

**MUST-FIX（实现/设计回写前必须处理）**

1. `FAILURE_PATTERNS` 并入后端 canonical 错误前缀（`[Error`、`Error`、`[Permission denied`、`[Approval denied`、`[Approval unavailable`、`[MCP tool error`、`[Task …]` 之后的 `status: failed`、非零 `exit_code:` 行），并把唯一未锚定的 `/failed\s+with\s+exit…/i` 收紧；补 node 用例（`[Error: …]` → error、`[Approval denied: …]` → error、`Grep` 结果行内含 `failed with exit status 128` → **ok**），浏览器 L4 改用真实 Bash JSON（`{"exit_code": 1, …}`）而不是 `[Exit 1] …`。
2. 失败时不要整体覆盖参数摘要：对 Bash/TaskOutput 这类结构化结果，保留命令/参数摘要，把失败信号落在 meta（如 `exit 1`）+ 错误色（必要时首行截断进 body 顶部）；改完补一条浏览器断言「失败行的 summary 仍含命令」。
3. args 也套 `formatBodyText(…, BODY_LIMIT)`；把 `arguments_truncated` 的「（参数已截断）」提示移出 hidden body（head 行或默认可见），并补一条**可见性**断言（`inner_text` 而非 `text_content`），顺带删掉 `createToolRow` 文档里从未实现的 `note` 参数。
4. `pendingToolRows` 兜底：`done`/`error` 分支清空；同名配对改取**最近**（队尾/`findLastIndex`）而非最早；补一条合成事件回归锁住「配对方向」（现在**没有任何测试**覆盖配对顺序，proposal R1 声称的「用 dispatch 写回归测试锁住顺序语义」是空头承诺——见 `tests/web_tests/test_transcript_view_browser.py` 全文与 `tests/web_tests/test_transcript_js.py` 全文，均无顺序/错配用例）。

**SHOULD-FIX**

5. L2 预算 4000 → ≤1200（或改结构断言），并订正 proposal.md 的「对照现状：≥ 100000 字符」为实测 ~24000（`agent/tool_result_display.py:50-55` + 被删除的旧 `addToolResultMessage`）。
6. 补 `test_server.py` 中真正缺失的两条：`transcript.js` 必须出现在 `index.html` 且（若设计坚持）位于 `chat.js` 之前；`.tool-row-note` 提示的可见性。
7. 回写 design.md：D2 导出清单（删 `summaryFromResult`、加 `updateToolRow`）、D4 与实现对齐（空结果 = ok）、D5 配对方向改为「最近」、D9 改「分段导轨」、D11 删掉「必须排在两者之前」的错误因果。
8. 顺手项（低成本、可测）：`onclose` 的 `bindActiveTab` 加 `tabs.has(tab.id)` 守卫；`formatCharMeta` 对 ≥1e6 走 `M` 单位；删除 `.message.tool` 死分支或注明保留原因。
