## 风险

- **D1 按字面实现会「改完仍红」**：`_flow_resolve_change_dir` 对带日期前缀的归档目录返回 `None`（89/89 归档目录都是这个形态）。若不改写 D1 就动手，新写的归档回归测试会直接红，浪费一轮；更糟的是 reviewer 若只看代码不看测试，会误判「已修」。
- **`repo_root` 推导错误会让归档测试逃逸到真实仓库**：`change_dir_for(_PROJECT_ROOT, …)` 实测指向真实仓库的 `openspec/changes/archive/<id>`。若实现这么写，tmp 冷状态测试会变红（或更坏：在真实仓库里创建目录）。必须在实现与测试里统一用 `CHANGES_ROOT.parent.parent`（或 `Path.cwd()`）。
- **事件落点与 manifest 落点分叉是静默的**：`write_review_manifest` 只接受 change **id**（不接受目录），所以两处解析必须由同一算法保证。前缀歧义（`alpha` vs `alpha-beta`）实测能选出**另一个 change** 的目录；分叉后 `verify_review_manifest` 会报 `tasks hash mismatch`（`tasks_hash` 取解析目录的 tasks.md），但只有跑校验时才发现。
- **跳过刷新对「已有已提交投影的归档目录」会留下永久 stale**（实测 1/89 命中）。当前无人校验归档投影 → 不一致被完全掩盖；盲区 B 一旦开启（或将来有人给 `--check-archived` 加 `verify_projection`）会突然爆出。见 Q3。
- **归档后 guard 的 change 映射静默失效**：`workflow_guard._current_change_id` 要求 `(CHANGES_DIR / branch_head).is_dir()`，归档移动后该目录消失，兜底又要求「恰好一个 active change」——本仓库有 3 个 active change，故返回 `None`，grill gate 与 awaiting gate 在收尾阶段**不再触发**。这是既存行为（#199 同样如此），但意味着「归档后仍可自由写代码」；本次不修，建议在 known-debt 记一笔或至少在 review 时知悉。
- **guard 硬拦一切「向 archive 写」的 Bash 命令且无事件豁免通道**（`mv`/`cp`/`mkdir`/`git add archive/...` 全部 exit 2，实测）。收尾必须用 `npx openspec archive`（命令文本不含受保护片段，exit 0）+ `git add -A`（exit 0）绕过；这条现状值得写进开发指南/收尾说明，否则下一个人会以为归档被门禁锁死。另注意 `git add -A` 会把 `#228` 类自愈产物一起吞进提交（本 change 的 D4 正是为了不再产生这类产物）。
- **本次口径只对「写通道」成立，不能外推**：spec delta 里「与 `flow status` 的既有口径一致」是**不成立的事实**（`flow status` 对归档 id 实测 exit 1）。若不按 Q1 推荐改文案，spec 会固化一条错误断言，并让后来者以为 `flow status` 可用。
