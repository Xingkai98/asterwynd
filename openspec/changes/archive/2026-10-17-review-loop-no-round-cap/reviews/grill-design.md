## 需要修改的设计点

- **Decision 2 的「收敛」判据不可判定，且两个 Scenario 互相矛盾**（`design.md:42-51`；spec delta `specs/dev-workflow-state-machine/spec.md:7`、`:9-25`）。Scenario「没有轮数上限」说「每一轮都有可修复的新问题 ⇒ 继续」，Scenario「无法收敛时报告阻塞」说「反复修复仍不断出现新的可证伪项 ⇒ 停下报告阻塞」；这两句描述的是**同一个可观察量**（又出现新项），却没有给出区分「净进展」与「空转」的任何判据。`design.md:50` 声称「两条都能在审阅报告里逐条对照」，但报告里没有任何字段/规则把「新项」折算成停或不停；因此「无法收敛」出口只能靠执行者主观判断，R1 的缓解并不成立。**场景裁定**：(a) 第 N 轮只提一条**风格建议**（既不是可证伪项、也不是必须修改项）时，按本设计的定义闭环**应当停**（不延长）；但现有 verdict 规则里 `PASS` 要求「无未解决中等以上问题」（`/home/happy/my-agent/.claude/commands/review-loop.md:62-63`），设计没有把「必须修改项」钉到这档严重度上，若审阅者因风格建议仍回 `CHANGES_REQUESTED`，规格要求「收敛即停 ⇒ PASS」就无法落地，闭环又没有上限，只能漂到「报告阻塞」。**怎么改**：明确 `必须修改项` = 审阅报告中「中等以上」的问题（与既有 verdict 口径对齐），风格/低价值建议只记录、不阻断 `PASS`、不延长闭环；并给「无法收敛」一个可对照的进度规则——最小改动是自然语言版的「最近两轮新增必须修改项数 ≥ 已关闭数（开放必须修改项数没有下降）⇒ 判定无法收敛，报告阻塞」。这条规则不引入数值上限，也不需要 witnessloop 的账本机制，但能把 Scenario 1 与 3 变成可判定、可复核的两条不同条件。(b) 若每轮都能找到一条真实但低价值的**可证伪项**并修掉，按现文案闭环会永远不停（每轮都有「新的可证伪项」）；按 Scenario 3 又应立即/迟早「报告阻塞」，但没有阈值说明何时算「反复」。**裁定：现设计对这条序列没有确定出口，`design.md:50` 的「可判定」断言不成立。** witnessloop 先例正是为此引入 B′（最近两轮累计净额 ≤ 0，`.../convergence-based-stop/design.md:167-182`），并在 `:576` 明确拒绝「只删掉 3、跑/PASS 为止」——理由是「那放弃终止保证」。本 change 现在选中的正是后者，只是加了一句主观的「无法收敛」出口。
- **漏改一条现行规格：`openspec/specs/change-documentation/spec.md:46-47` 与 `:94` 仍写着「until `PASS` or a round cap is reached」**。这是**现行**规格（不是 archive），且同一段 `:49-50` 又写「re-review until convergence」，文件内部已经自相矛盾；`openspec/specs/dev-workflow-state-machine/spec.md:258` 的设计阶段闭环则写「再审直到收敛」。也就是说，不只是 proposal 说的「两半流程两套口径」，**设计阶段闭环本身就有两套现行规范**。本 change 的 Impact Analysis（`proposal.md:50`）只列了 `dev-workflow-state-machine`，tasks 2.2 也只同步那一份；若不改 `change-documentation`，归档后会留下两条互相冲突的现行 Requirement。**怎么改**：在该 capability 增加 MODIFIED delta（或同 PR 直接改这两处 Requirement/Scenario），把「round cap」替换为收敛口径；tasks、Impact Analysis 与 T 扫描面同步补上该文件；因为它在 `openspec/specs/**` 受保护路径内，`workflow-events.jsonl` 的 `current_spec_synced` 事件需覆盖**两份**规格（或各写一条）。
- **T6 的验收判据自带假阳性，永远无法达到「无命中（exit 1）」**（`design.md:128`；`tasks.md:37`）。实测原命令 `git grep -n "3 轮封顶\|轮数封顶" -- ':!openspec/changes/archive'` → **exit 0，32 行命中**：其中 9 行是本次要改的现行口径（`AGENTS.md:18,104`、`README.md:148`、`docs/interview-script/questions/Q14-dev-process.md:13,56`、`docs/requirements-process.md:45,189`、`scripts/check_openspec_artifacts.py:1139,1623`），1 行是历史记录（`docs/openspec-change-backlog.md:173`），其余 22 行是**本 change 自己的 proposal/design/tasks 在引用旧口径**（例如 `design.md:7`、`proposal.md:24`、`tasks.md:20`）。改完全部现行落点后，前 9 行消失，但后 23 行仍在，命令仍 exit 0。它还漏掉了英文与变体：`README_EN.md:148` 的「a 3-round cap」、上述 `change-documentation` 规格的「round cap」、`docs/openspec-change-backlog.md:169` 的「4 轮封顶」。**怎么改**：扫描面不要用「全仓减 archive」，而是显式限定现行规则文件（`AGENTS.md`、`README.md`、`README_EN.md`、`docs/requirements-process.md`、`docs/interview-script/questions/Q14-dev-process.md`、`scripts/check_openspec_artifacts.py`、`openspec/specs/**`），或同时排除 `openspec/changes/review-loop-no-round-cap/**` 与 `docs/openspec-change-backlog.md`；模式至少覆盖 `3 轮封顶|轮数封顶|4 轮封顶|round cap|3-round cap`；并在 design 里像 witnessloop 那样**点名** `backlog:169/173` 与 `Q14:17` 是历史记录、不属于扫描面，避免下一个人误红或把扫描面写宽。
- **T7 与 R4 自相矛盾，且缺少时序**（`design.md:111,129`；`tasks.md:38`）。实测**归档前** `git diff --stat origin/master...HEAD -- openspec/changes/archive/` → **空输出、exit 0**（HEAD `8eb324d`，`origin/master` `79460e3`，0 behind / 1 ahead；archive 工作区无未跟踪改动）；而 T7 的期望是「只出现本 change 自己的归档路径」，R4 的期望却是「必须为空」。两者分别只在归档**前/后**成立，文案却没有时序。**怎么改**：拆成 T7a（归档提交前：输出必须为空，证明没有回填历史）与 T7b（归档纯 rename 提交后：只出现 `openspec/changes/archive/2026-10-17-review-loop-no-round-cap/`）；两条都写明前置是「对应提交已落盘」，因为 `git diff` 看不到未提交/未跟踪内容。
- **对 witnessloop 先例的转述不准确，且「只对齐停的条件」这条边界被写窄了**（`proposal.md:72`；`design.md:55-62`）。实测 `/home/happy/wl-wt/convergence-based-stop` 的 change 目录**完全未提交**：`git ls-files openspec/changes/convergence-based-stop/ | wc -l` = 0，`git status --porcelain` 为 `?? openspec/changes/convergence-based-stop/`，分支 `convergence-based-stop/2026-10-15`；其 `proposal.md:8` 自述「草稿…用户停轮尚未做」，`design.md:9` 的 `## 8. Open Questions` 三条未裁定。所以「witnessloop **已经**把它自己的审阅闭环…改成收敛即停」是事实错误（它只是**未合入、未停轮确认的设计稿**）。另外 proposal 引用的「另一个环先把封顶写成停轮理由、之后又跑 R4–R6」在该先例里被明确标为「**时点旁证、在审 revision 之外、未提交**」（其 `design.md:73-108`、`:115`），不是「仓内记录」；只有「3 轮 cap 下跑到 R5」是可在 `ef8b3ab` 复核的实录（其 `proposal.md:60-70`）。**更关键的边界问题**：先例的「停的条件」包含 B′（最近两轮累计净额 ≤ 0），而本 change 的「停的条件」只有 PASS/「没有新的可证伪项」；B′ 恰恰是「仍在冒新问题但净进度不为正」时的停机判据。Decision 3 说「只对齐停的条件、不搬机制」——账本/证明确实是机制，但 **B′ 是条件本身**，本 change 把条件也丢了。**怎么改**：把「已经改成」订正为「未合入的设计先例」；引用 R4–R6 时加「时点旁证」限定；Decision 3 二选一——要么在自然语言层面补一条 B′ 式净进度判据（与上一条 M1 合并处理），要么明确承认「本 change 的终止保证弱于先例，不声称完全对齐」，不要既引用先例又丢掉先例的核心判据。
