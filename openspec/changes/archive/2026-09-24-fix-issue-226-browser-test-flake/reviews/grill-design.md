- **Q2**: 根因 B 回归测试的注入延迟取多少毫秒，以及它是否可以调用 `_ensure_workflow_view`？design D4 只写「判别力 = 不修 `_wait_app_ready` 必红」，但没有钉住参数，而这正是判别力成立与否的分水岭。具体例子：设 `page.route` 延迟 `D`，回归测试 = `_wait_app_ready` → 派发 → 断言 svg 可见。**(i) D = 1500ms**：未修版（旧 helper = 5s 超时 + 300ms）在 5.3s 才返回，此时 init 早在 1.5s 完成，派发后视图不会被抢 ⇒ **未修也绿**，变异验证做不出来；**(ii) D = 6000ms**：未修版 5.3s 派发 → 6.0s 时 `showHub()` 抢走 active → svg hidden → 5s 内超时 ⇒ **未修必红** ✓；**(iii) 若回归 B 照抄「已验证 3 条」的两层写法（也调 `_ensure_workflow_view`）**：第二层会在派发后把视图强行拉回激活 → **未修也恒绿（自证）**。选项：钉 `D ≥ 6000ms`（推荐，旧 helper 的固定耗时是 5.3s，必须显著超过）且回归 B **只用**修后的 `_wait_app_ready`、禁用 `_ensure_workflow_view`；或在测试里显式断言「注入生效」（如 barrier 实测等待 ≥ D）以免未来命令失效后静默失去判别力。

- **Q5**: D1.2 的 `init().then(ok, () => {})` 第二参数（吞掉 init 的拒绝）是否改为不带 `onRejected`？具体例子：今天 `init();`（`web/static/chat.js:2119`）在 `init()` reject 时（例如 `setupHub()` 抛错）会产生未处理的 promise 拒绝（Chromium 报 `Uncaught (in promise)`，`tests/web_tests/test_workflow_graph_browser.py:62,65-66` 的 `pageerror` 收集器可能把它直接记成测试失败）；改成带第二参数的写法后，同一次失败**不再冒头**，测试改为等 15s 屏障超时 —— 失败正文从真实 JS 错误退化为一条超时。前后对比：**(a) 现状**：立刻报真实错误；**(b) 提案**：15s 超时 + 真实错误被吞（且 D1.2「只为不发散 unhandled rejection / 不新增噪声」的措辞前提不成立：噪声是今天**已有**的，不是本 change 新增的）；**(c) `init().then(setTrue)`（不带第二参数）**：成功时置位、失败时保持今天的响亮失败 —— 这才是真正的「只增不改」。选项：(c) 推荐；若坚持 (b)，须把 D1.2 的措辞改成「本 change 会**抑制**既有的 init 失败信号，改以屏障超时呈现」并接受可诊断性下降。
