## Code-Resolved Questions

- **归档点门是否会在最终归档 commit 跑到？** 会。第一处 checker 调用 `--base-ref "$BASE_REF" --require-base`，没有 `--check-archived`；`main()` 在 `not args.check_archived and not args.change` 时调用 `_check_new_archived_completion_gates`，后者用 `git diff --name-only --diff-filter=AR <base>` 并排除 base 树已存在的目录。归档 move 以 rename 出现，`AR` 覆盖 `R`。证据：`scripts/check_openspec_artifacts.py:1484-1544,1664-1686,1766-1774`；`.github/workflows/ci.yml:84-89`。此前 #235 的实测（`test_archived_gate_ar_catches_pure_rename_where_a_only_misses`）也锁过该行为。
- **删除 `_check_review_manifests` 是否会误删非 manifest 判据？** 会，如果整函数删除。该函数内同时包含 building-review 存在性门（`:1129-1140`）与 `*-review.md` → manifest 校验（`:1142-1152`）。设计 Decision 1 已正确拆分：存在性门必须保留，manifest 循环删除。`_check_archived_completion_gate` 本来就单独持有归档侧的存在性门（`:1616-1624`），不受影响。
- **`--check-archived` 删除 manifest 校验后保留什么、消失什么？** 保留：遍历 `archive/*`、逐 change 跑 `_check_archived_projectable`（`:1732-1748`）。消失：`verify_review_manifest` 调用（`:1741`）、`tasks_hash` 跳过计数与 stderr 汇总（`:1735,1742-1746,1749-1754`）。`_check_archived_projectable` 本身不读 manifest，零改动（`:1156-1170`）。
- **`_check_archived_completion_gate` 增加 verdict 是否越界？** 不越界，但它是「等价替代」而非「其它检查不变」：旧 `--check-archived` 对**全部历史归档**做 PASS 门，新门只对**本 PR 新建归档**做 PASS 门；对新建归档语义等价，对历史则是有意的收窄。设计 Decision 3 与 proposal 需求 4 已正面写明「历史不追溯」，但 proposal 需求 6 的「其它检查行为不变」应补一句「`--check-archived` 的历史漂移检测被有意移除」，否则两处口径冲突。
- **历史 79 份报告的证据是否成立？** 核心成立：79 份归档 `building-review.md` 中确实只有 1 份（`2026-10-17-round-model-align`）含 `## 闭环出口`。但数字要修正：实测 67 份含 `## Verdict` 前缀标题、12 份没有；按「最后一个 `## Verdict` 小节的首个 token」统计是 62 PASS / 5 CHANGES_REQUESTED / 12 无标题，且有 15 份该小节同时出现多个 token（如 `CHANGES_REQUESTED` 与 `PASS`）。proposal 的「78 份使用 `## Verdict`」与 design 的「53 / 13 / 1 / 12」无法用同一规则复现，需写明抽取规则或改正数字。证据：本报告执行的 Python 统计（基于 `openspec/changes/archive/*/reviews/building-review.md`）。
- **旧 manifest 校验的作用面是否只有 `building-review.md`？** 不是。旧代码对 `reviews/` 下**每一份** `*-review.md` 都要求同名 manifest 且 `verdict == PASS`（`:1150-1152`；`agent/workflow/review_manifest.py:158-159`）。新检查只读 `building-review.md`，因此 `reviews/design-review.md` 若存在，其 PASS 门会消失。历史上只有 1 份 design 形态 ast manifest（issue #316 §4.1），且当前流程不要求 `design-review.md`，所以影响面窄；但 proposal「唯一不被覆盖的判据是 verdict」的表述必须限定为「building review 的 verdict」。
- **active 侧触发条件真的与新旧完全一致吗？** 不完全一致。旧代码只要 `reviews/` 存在，就对其中 `*-review.md` 跑 manifest 校验，与 change 类型、spec delta、tasks 是否勾选都无关（`:1142-1152`）；现存测试 `test_check_change_rejects_review_report_without_manifest` 用一个 docs change + `building-review.md` 就断言 `review manifest missing`，正是旧作用面的证据（`tests/test_openspec_artifact_checker.py:211-220`）。新设计的触发条件是「非 docs + spec delta + tasks 全勾」。这是一次有意的收窄（避免 partial review 被误伤），但 design `:98-108` 的「触发条件保持…完全一致」说法不准确，应改为「building-review 存在性门的触发条件不变；manifest 校验的隐式宽触发被收窄为完成面」。
- **保留 `review_manifest.py` / CLI / `flow-policy` 会不会产生矛盾？** 行为上没有矛盾：删除后 checker 不再 import `verify_review_manifest`，该模块没有其它生产消费者；`flow-policy.json:55-59` 与 `workflow_guard.py:81` 只是继续把 `-review-manifest.json` 当受保护路径，保留是安全的。文字上有矛盾：`specs/dev-workflow-gate/spec.md:7` 同时写「SHALL NOT 再被要求、产出」和「写通道…保留」。应把「产出」改成「流程要求产出」，并明确 CLI 只是 legacy 通道。
- **三份 witnessloop manifest 是否足够？** 足够。`validate_review_manifests` 对每个 target 至少有 manifest 的要求（`contract.py:531-538`）；`grill_evidence_findings_in_change` 对每个 target 跑 grill 正文判据（`checkcmd.py:182-187`）；`code_hits` 为真时再加 grill-adversarial 与 building 两份 stage manifest（`checkcmd.py:190-207`）。本 change 改 `scripts/**`，`code_hits` 必真。孤儿规则会把 `reviews/**/*.md` 全部纳入绑定检查（`contract.py:548-575`），所以 `grill-design.md` / `grill-adversarial.md` / `building-review.md` 三份报告都要被 `report_path` 覆盖。
- **`change-documentation` spec 是否需要 delta？** 不需要。该规格只在 `:406` 提到 `review-manifest` 作为受保护写入通道可用；本 change 保留该 CLI 与受保护规则，口径仍成立。需要改的是 `dev-workflow-gate`、`dev-workflow-state-machine`、`platform-gate` 三份 delta 与对应 current spec。
- **`README_EN.md` 是否必须同改？** 必须。`AGENTS.md` 维护规则要求 `README.md` 改动必须在同一变更同步 `README_EN.md`；两处对应句分别在 `README.md:153` 与 `README_EN.md:153`，tasks 3.2 已覆盖，不能只改中文。
- **测试基线如何？** `uv run pytest tests/test_openspec_artifact_checker.py -q` 实测 130 passed（5.79s），`PYTHONPATH=. uv run python scripts/check_openspec_artifacts.py` 与 `--check-archived --skip-protected-paths --skip-backlog` 均 exit 0。基线干净，新测试的红/绿信号不会被既有失败污染。
- **解析规则能否被平凡绕过或产生假红？** 两种都会，取决于实现：`\bPASS\b` 逐字搜索会把「不是 PASS」判成通过；把小节内所有 token 一起统计会把 `PASS（此前 CHANGES_REQUESTED 已收口）` 判成多 token 假红（历史 15 份 `## Verdict` 小节正是多 token 形态）。因此需要决策 7 的四条规则；只读首个非空行、要求以 `PASS` 开头，可以同时消掉这两类问题。
