### 发现

- **Issue 1（severity: high）**: Decision 8「群聊会话内 pending 交互显式降级」在文本上收窄了既有 `web-ui` 的两条**无条件** Requirement，但 delta 只有 `## ADDED Requirements`、没有 MODIFIED，且四条新 Requirement 里**一个字都没提** pending 降级 —— 同步之后 web-ui 规格会自相矛盾。；证据: `openspec/specs/web-ui/spec.md:362`（「Web UI run SHALL 将需要审批的工具调用暴露为 pending approval request」）、`openspec/specs/web-ui/spec.md:1122`（「Web session SHALL 把 pending 提问/审批当作 session 级状态…WebSocket 断开 SHALL NOT 让…失败」）；对照 `openspec/changes/web-agent-group-chat/specs/web-ui/spec.md:1-55`（只有 ADDED，无 pending 相关条目）、`openspec/changes/web-agent-group-chat/design.md:86-91`、`tasks.md:29`。；影响: 人设单聊会话与群内会话都是货真价实的 Web session（`web/session.py:1617-1704` 由同一 `_create_session` 造、同一 `SessionStore` 落盘、走同一 WS），按现状文本它们仍受「必须暴露 pending」约束；而 Decision 8 明写「审批类调用按 fail-closed 立即判定为 unavailable」。规格集在归档后对「内部会话」这件事是假的，且 `check_openspec_artifacts.py` 不校验这类漂移。；建议: 在 web-ui delta 里加一条 MODIFIED（对上述两条 Requirement 显式加 scope 限定「内部会话除外」），并在 spec 里给「撤 ask 类工具 + 审批立即可用性判定」写上可测 Scenario。**行为侧不需要新口径**：`openspec/specs/agent-runtime/spec.md:356-362` 已有「审批不可用时 fail closed」的 Scenario 可直接引用。

- **Issue 2（severity: high）**: 成员 run 的失败 / 超时 / 被拒语义没有设计，且**房间级并发**没有互斥设计 —— 而 tasks 3.6 正要把这个语义**冻结**成 `SessionRunner.run(session_id, message) -> final_text`。；证据: `design.md:55-59`（接口定义）、`design.md:104-109`（轮次终止只覆盖「所有 slot 走完 / 触上限」两种正常路径）、`web/session.py:1770-1782`（同 session 并发 run 被拒时只发 `run_in_progress` 事件后 `return`，**不产生任何新文本**）、`web/session.py:1736-1757`（`run_session` 返回 `None`，final_text 只能靠旁路取）、`openspec/specs/web-ui/spec.md:543-551`（该拒绝是既有既定行为）。参照实现对此有显式三态与超时：`ds-bot/src/host/groups.js:178-179` 注释「resolves to its final text, `{ failure }` when its model call failed, or null when it did not answer in time or the round was stopped」+ `ds-bot/src/host/constants.js:25` `ROOM_REPLY_TIMEOUT_MS = 240_000`。；影响: ①两个浏览器标签同时打开同一房间（或用户连发）⇒ 两轮次并存 ⇒ 成员 session 的 run_lock 拒掉其中一个 ⇒ 若 `final_text` 退化为「读 session 最后一条 assistant」，编排器会把它当**本轮发言**写进房间日志 → 陈旧内容重复入日志，或与 Decision 10 的静默判定混淆；②成员 run 抛异常（LLM 错误、工具异常，或 `agent/memory/persistent.py:441-465` 的 `_git_commit` 在 git 缺失/提交失败时抛 `RuntimeError`）时，该 slot 算不算「走完」、要不要记房间日志、要不要中止整轮 —— 全无定义 ⇒ 轮次可能挂死或静默跳过。tasks 2.2/2.7 无法为这些路径写出期望值。；建议: 在 design 补一节「成员 run 三态（正常文本 / 静默 / 失败）+ 单轮超时 + 房间级互斥（同房间同时至多一轮）」，并明确 `SessionRunner.run` 的失败是**返回值**还是**异常**（若为返回值，必须与「取 session 最后一条 assistant」明确区分，否则静默错答）；spec delta 的「群聊轮次终止」Requirement 需一并覆盖失败与超时出口。

- **Issue 3（severity: medium）**: 内部会话的删除保护只覆盖 `DELETE /api/sessions/{id}`，WS `reset` 是**第三条删除通道**，而且它会**换掉 session id**，直接破坏 Decision 7 的稳定映射。；证据: `web/server.py:724-760`（`reset` → `session_manager.remove_session(session.session_id)` → 再 `create_session_async(...)`）、`web/session.py:1709-1727`（`remove_session` 落盘删除：`self._store_for(ws).remove(session_id)`）、`agent/session.py:208-221`（`remove` = `shutil.rmtree(session_dir)`）、`web/session.py:1627`（新 id 走 `new_session_id()`，即随机值）、`design.md:82`（保护清单只列 `GET /api/sessions` 过滤与 `DELETE` 拒删）、`openspec/changes/web-agent-group-chat/specs/web-ui/spec.md:40-55`（Requirement 只写「会话删除接口」）。；影响: 人设单聊会话按 Decision 2/9 走既有 `/ws/<session_id>`，任何 WS 客户端发 `{"type":"reset"}` 就能删掉底座快照并把新 id 换成随机值 → roster 里记的「persona → 单聊会话 id」变悬空、「单聊内容不污染」与「内部会话受保护」两条验收都可被绕过（前端目前没有发 reset 的入口，但协议可达，且 `tests/web_tests/*` 在用这一路子）。；建议: 把保护口径从「删除接口」升为「任何会销毁内部会话底座的路径」，在 design 与 spec 里显式写：内部会话拒绝 `reset`（或 reset 后仍复用原 session id 并回写 roster）。

- **Issue 4（severity: medium）**: Chief/admin 的**归属在 design 内部自相矛盾**，且 spec delta 与 tasks 都没有任何东西承载它 —— 而「用户消息默认由 Chief 应答」是一条 spec Requirement。；证据: `design.md:106`（「每轮上限 = 成员数 + 固定额外轮次（**群有 admin 时**再加固定额度）」⇒ 群属性）vs `design.md:120`（「`mainBotIds` 是 **roster 上的 id 列表**」⇒ 人设/花名册属性）；`openspec/changes/web-agent-group-chat/specs/multi-agent-collaboration/spec.md:48`（「用户消息 SHALL 默认由群管理员（Chief）应答」）；`tasks.md:22`（3.1 的 roster 字段只有「稳定 id、名称、角色、指令、模型绑定」，无 admin/chief）；参照实现其实**两者都有且不同**：`ds-bot/src/host/groups.js:261-262` 的 `room.admin ?` 是**房间**属性（门控 `ROOM_ADMIN_EXTRA_TURNS`），`ds-bot/src/host/prompt.js:25-36` 的 `MAIN_RULES` 才是 roster 级的「Main Bot (Chief of Staff)」且明写「The team can have more than one Main Bot」。；影响: 「Chief 从哪来 / 存在哪 / 能否多个 / 是不是群属性」不定，则 (a) spec 的「默认由 Chief 应答」写不出断言；(b) Decision 11 的预算公式挂在一个未定义的「群有 admin」上；(c) 实现会各自发明（花名册布尔位 vs 房间成员表）。；建议: 在 Decision 里二选一定死并回写 spec（Requirement 需说明 Chief 如何被指定），tasks 3.1 补对应字段任务。

- **Issue 5（severity: medium）**: roster 与房间日志的**持久化位置未定**，与多 workspace（allowlist）模型的交互完全没涉及 —— 而「跨进程持久化」是一条 spec Requirement。；证据: `design.md:63`（「随房间记录持久化」）、`design.md:80`（「分别存 roster 与房间记录」）、`proposal.md:39`（只在 `agent/` 说「新增…持久化」，无路径）；项目里并存两种落点约定：会话按 **workspace** 存（`web/session.py:1422-1433` 每 workspace 一个 `SessionStore`；`web/server.py:291-318` workspace allowlist/hub 分区），记忆与资产按**仓库哈希**存（`agent/memory/persistent.py:18,180-185`、`agent/subagent/workflow_assets.py:31-38`）。；影响: 若 roster 落在 `~/.asterwynd/projects/<hash>/`（仓库级）而人设会话落在 `<workspace>/.asterwynd/sessions/`（workspace 级），用户切到另一个 allowlist workspace 时 roster 里的会话 id 全部悬空；hub 过滤也必须按 workspace 正确实现。这是 spec 的「跨进程持久化」与 tasks 2.1（跨重启恢复）能否写出确定断言的前提。；建议: 在 design 里定死路径与作用域（建议 workspace 级，与会话同域，避免悬空），并说明与多 workspace 的关系。

- **Issue 6（severity: medium）**: Decision 5 的房间日志「切片注入」规则与它自己引用的参照实现**语义不同**，而且**注入切片无上限** —— 静默成员会被反复重复注入同一段内容，上下文可无界增长。；证据: `design.md:66`（「成员本轮看到的 = 房间日志中『**该成员上次发言之后**』的切片 + 本轮发言序位说明（参照 DS Bot 的 `unseenLines` / `roomPrompt`）」）；参照实现实际用的是**持久化游标** `room.seen[memberId]`，且在**回合开始时**推进（`ds-bot/src/host/groups.js:44-45` 的 `unseenLines` 读 `room.seen[memberId]`，`:183` 在 `roomTurn` 开头就 `room.seen[member.id] = room.seq`，即**静默/超时回合也推进**）；参照还有明确的切片上限与分层：`:21-23` 的 `ROOM_FIRST_LOOK = 12` / `ROOM_DELTA_MAX = 24` / `ROOM_EARLIER_MAX = 8`、`:154-155` 把「本轮」与「往轮（context only）」分开、`:170` 的「Nothing new in this round since your last message.」。；影响: 按 design 的规则，一个连续静默（或从不发言）的成员其切片边界永不推进 ⇒ 同一段日志在它每一轮都被重新注入它的会话（重复内容 + 上下文膨胀 + token 成本随静默次数线性增长）；参照的 `seen` 游标正是为避免这一点而存在。又因为 design 没有 FIRST_LOOK/DELTA 上限，跨多轮后单次注入可以无界（与本仓 issue #278「上下文无界致 OOM」同类风险）。tasks 2.2 的静默用例不会暴露它（它只断言「不发布消息」）。；建议: 把注入规则从「上次发言之后」改为「上次**回合**之后」（游标在回合开始/结束推进，含静默回合），并在 design 里给切片加上限与「本轮 vs 往轮」分层。

- **Issue 7（severity: medium）**: `@` 的解析位置与「轮次 slot 序列」都没有钉死，导致 spec 自身口径不一致，且 tasks 2.2 要求的「轮次顺序 / 轮次终止」写不出确定断言。；证据: `openspec/changes/web-agent-group-chat/specs/web-ui/spec.md:17`（用户「输入以 `@<名称>` **开头**的消息」）vs `openspec/changes/web-agent-group-chat/specs/multi-agent-collaboration/spec.md:69-74`（「**某成员发言中**点到不在成员列表中的名字、点到自己、或点到多个成员」⇒ 句中 `@` 对被解析）—— 同一天里「用户消息要求行首、成员发言可在句中」这条差异没有任何 Requirement 说明；`multi-agent-collaboration/spec.md:48`（用户消息默认由管理员应答）与 `:54`（被 `@` 者「SHALL 成为本轮**首先**发言的成员」）叠加后，Chief 与 @ 者的先后无定义；`design.md:104-107` 的终止条件写「一轮在所有 slot 走完（或触上限）时结束」，但 **slot 序列本身没有定义**（是「每成员各一槽」？`@` 的人追加到队尾？同一人被 @ 两次算几个槽？）——参照实现里 slot 是显式的 `round.slots`（`ds-bot/src/host/groups.js:172-173` 把完整发言顺序与「你是第 N 位 / 前面几位已发言」注入给成员）。；影响: tests 2.2 是 must-pass 的编排测试，没有确定的 slot 序列就写不出期望值；实现会各自发明 @ 的入队语义（前插 / 追加 / 去重）与「一轮何时结束」。；建议: 在 design 里定死 `@` 解析（用户行首 vs 成员句中的差异要明说）与 slot 序列算法（初始槽 = 谁、@ 如何入队、去重规则、`轮次上限 = slots + 固定额度` 里的 slots 是哪一份），并同步进 spec 的 Scenario。

- **Issue 8（severity: medium）**: 删除人设 / 房间的级联语义（内部会话、房间日志、**persona 记忆目录**）无 Requirement、无 Decision、无 task；而 web-ui delta 已经引用了一个「人设/房间删除接口」，却没有任何 Requirement 定义它。；证据: `openspec/changes/web-agent-group-chat/specs/web-ui/spec.md:50-55`（Scenario 的 THEN 写「人设 SHALL 只能经**人设/房间的删除接口**清理」）——该接口在 delta 中不存在；`design.md` 全文无删除级联决策；`tasks.md` 无删除任务；牵连 `design.md:73` 的 persona 记忆落点 `<project-hash>/memory/personas/<persona-id>/`（删除人设后记忆长期残留）。；影响: ①「不可直接删除」这条验收的反面（正当删除路径）没有规格可依；②删除人设后 persona 记忆仍留在本机磁盘，是未声明的隐私面；③proposal 的 Goal 写了「长期 agent 人设的…**Web 管理**」，但 web-ui delta 只有 4 条 Requirement（群聊视图 / 按来源区分 / 单聊群聊共存 / 内部会话不列出），**没有任何 roster/房间 CRUD 的管理入口 Requirement**，也没有「如何进入单聊视图」的 Requirement（只在共存条里被引用）。；建议: 补 web-ui delta 的 roster/房间管理 Requirement（含删除及其级联：会话底座 + 房间日志 + persona 记忆）与相应 tasks；同时明确单聊视图的入口。

- **Issue 9（severity: medium）**: Decision 6 把「先补 Web 记忆接线」写成单参数注入，实际需要 2–4 个参数的**忠实移植**，否则人设记忆会以半接线形态落地（策略与 CLI 不一致、无 LLM 去重判官）。；证据: `design.md:71`（「在**人设会话**的构造成本中注入 `persistent_memory`…**该参数两处都支持**」）；`web/session.py:1648-1664` 目前**只**传了 policy/mode_policy/ignore_patterns/code_intelligence/web_search/browser/mcp_manager/tools/selection_config/read_output_config/sandbox —— 未传 `persistent_memory`，也**未传 `memory_config` / `quality_config` / `llm`**；对照 `agent/main.py:270-289` 的 CLI 同款调用传了 `persistent_memory=` + `quality_config=` + `memory_config=config.memory` + `llm=llm`；`agent/tools/factory.py:163-173`（`_build_memory_dedup_judge`：`llm is None` ⇒ **直接返回 None**，即 Web 侧没有 LLM 去重判官）、`agent/tools/factory.py:317-327`（不传 `memory_config` ⇒ 一律回落默认 `MemoryConfig()`，archive/decay/摘要参数与用户配置脱钩）。；影响: 「先补接线再加维度」的产物会是与 CLI **不同策略**的记忆（无 LLM 去重、衰减/归档参数用默认值），tasks 2.4 的「并发写记忆」用例也会跑在这套偏离的配置上；这类偏离在后续排查里极难归因。；建议: 在 Decision 6 / tasks 3.7 里把接线清单写全（`persistent_memory` + `memory_config` + `llm`（+ `quality_config` 是否要）），并明确「普通 Web 会话仍然只注 `persistent_memory` 还是完全不注」。

- **Issue 12（severity: low）**: 本轮次开启规则与所引参照实现是**故意分歧**，但既未声明也未论证，读 RIR 的人会以为照抄。；证据: `design.md:107`（「用户再次发言才开启新一轮」）与 `specs/multi-agent-collaboration/spec.md:82-85`（「SHALL NOT 在用户再次发言前自行开启新一轮」）vs 参照实现 `ds-bot/src/host/constants.js:53-54`：`// Rounds Bots may start in one group by posting, before the user speaks there again.` / `export const ROOM_BOT_ROUNDS = 3`（成员**可以**自己开轮次，上限 3 轮），以及 `groups.js:162` 的 `round.kickoff` 分支。；影响: 不算缺陷（本设计更保守），但 RIR 的 design impact 应显式记「本 change 收紧为仅用户开轮，理由：…」，否则后续容易被当成漏实现。；建议: 在 Decision 11 或 RIR 里补一句 divergence 声明与理由。
